
# The Invisible Healer
## Phase 04 — Database Migration Policy

### 1. Purpose

Alembic is the only approved mechanism for changing
the application's PostgreSQL database schema.

All application database changes must be:
- Version controlled
- Reviewed before execution
- Reproducible
- Tested against an isolated database
- Compatible with the existing ORM models

### 2. Ownership

SQLAlchemy defines the application schema.

Alembic manages schema revisions.

Supabase PostgreSQL is the system of record.

The FastAPI application must never automatically
create or migrate tables at startup.

Do not use Base.metadata.create_all() in production.

### 3. Migration Naming

Every migration must have a meaningful name.

Examples:

0001_initial_baseline.py
0002_create_admin_users.py
0003_create_admin_sessions.py
0004_create_roles_permissions.py

The initial baseline has the explicit ID 0001.

All later revisions should normally use
Alembic's generated unique revision identifiers.

Use descriptive slugs.

### 4. Creating a Migration

After adding or changing ORM models:

1. Import the models into Alembic metadata.
2. Check that the database is at the current head.
3. Generate a new migration.
4. Review its upgrade() implementation.
5. Review its downgrade() implementation.
6. Test migration on an isolated PostgreSQL DB.
7. Run schema drift checks.
8. Commit both models and revision files.

Command:

python -m alembic revision --autogenerate \
    -m "create_admin_users"

### 5. Review Policy

Autogeneration is a proposal, not approval.

Review all operations, including:

- create_table
- drop_table
- add_column
- drop_column
- alter_column
- create_index
- drop_index
- foreign key modifications
- unique and check constraints
- nullable changes
- server defaults

Never apply autogenerated DROP operations
without manual review.

### 6. Supabase Safety

Supabase-managed schemas and unrelated tables
must not be controlled by application migrations.

Application migration ownership is defined
by registered SQLAlchemy metadata and the
migration configuration.

Review all migration scripts manually because
autogeneration filters do not constrain manually
written operations.

Do not run experimental migrations on production.

### 7. Forward Migration

Before applying an upgrade:

1. Confirm database environment.
2. Confirm current migration revision.
3. Back up the database when appropriate.
4. Verify the backup can be restored.
5. Review the new revision.
6. Run the upgrade.
7. Verify the resulting revision.

Commands:

python -m alembic current
python -m alembic upgrade head
python -m alembic current
python -m alembic check

### 8. Rollback Policy

Test a rollback on an isolated PostgreSQL
database before deployment.

Example:

python -m alembic downgrade -1

Some changes are not automatically reversible.

Examples include:
- Data deletion
- Dropped columns
- Destructive type conversions
- Removed constraints with dependent data

For production incidents, restoring verified
backups or applying a corrective forward
migration may be safer than downgrading.

A downgrade is not automatically a data backup.

### 9. Schema Drift Detection

Use:

python -m alembic check

This compares database schema against
registered SQLAlchemy model metadata.

It can detect many pending autogenerated
schema operations.

It does not guarantee detection of every
database-level change or clinical data problem.

Keep migration history checks, ORM checks,
and dedicated integration tests in CI.

### 10. Existing Database Baseline

The initial revision is intentionally empty.

Only apply it to a database whose existing
application schema has been inspected.

If a database already has application tables,
review their ownership and schema compatibility
before marking the baseline.

Do not stamp an unknown database as current.

### 11. Production Deployment

Recommended sequence:

1. Create a verified backup.
2. Stop or restrict incompatible writers.
3. Execute approved migrations once.
4. Verify revision and schema.
5. Deploy compatible application code.
6. Run application health checks.
7. Monitor errors and performance.

For non-backward-compatible changes, use an
expand-and-contract migration strategy.

### 12. Phase Boundaries

Phase 04 provides only:

- Migration configuration
- Schema version tracking
- Initial empty revision
- ORM metadata integration
- Autogeneration
- Migration governance
- Drift checking
- Migration tests

Phase 04 does not create clinical models.
